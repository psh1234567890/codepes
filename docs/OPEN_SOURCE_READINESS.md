# 오픈소스 지원 프로그램 준비 상태

## 목적

이 문서는 CodePes를 공개 오픈소스 프로젝트로 운영하고 지원 프로그램에 신청하기 전 필요한 증거와 남은 작업을 구분합니다. 특정 프로그램의 선정이나 자격을 보장하지 않습니다. 신청 시점에는 반드시 해당 프로그램의 최신 공식 요건과 약관을 다시 확인해야 합니다.

## 신청 전에 쌓아야 할 운영 증거

지원 프로그램은 단순히 공개된 코드보다 실제 오픈소스 운영과 사용자 가치를 중요하게 볼 수 있습니다. 다음 자료를 과장 없이 준비합니다.

### 프로젝트 가치

- 어떤 사용자가 어떤 문제를 겪는지
- 기존 대회 목록과 비교해 CodePes가 주는 이점
- 공식 출처 우선, 시작 시각 구분, fallback 같은 신뢰 설계
- 학생, 동아리, 교육자, 개발자에게 유용한 실제 사용 사례

### 공개 개발

- 공개 이슈와 Pull Request에서 이루어진 의사결정
- 외부 기여자가 재현 가능한 설치·테스트 절차
- 버그 수정과 릴리스가 연결되는 변경 기록
- `good first issue`와 명확한 기여 범위

### 유지관리

- 데이터 오류 제보와 검토 절차
- 보안 신고와 의존성 업데이트 과정
- 정기 데이터 작업 실패를 확인하는 방법
- 단일 유지관리자 의존도를 낮추기 위한 계획

### 사용 지표

분석 도구를 추가하기 전 개인정보 문서를 먼저 갱신하고 사용자 동의와 최소 수집 원칙을 정합니다. 초기에는 다음과 같은 공개적이고 비침해적인 증거를 우선할 수 있습니다.

- GitHub stars, forks, watchers
- 고유한 외부 기여자 수
- 해결된 이슈와 Pull Request 수
- GitHub Release 다운로드 또는 공개 배포 피드백
- 동아리·학교·커뮤니티의 공개 사용 후기

숫자가 작더라도 추정치를 실제 값처럼 쓰지 않습니다.

## 신청서 초안에 포함할 내용

1. **한 문장 설명**
   한국 개발자가 공식 출처 기반의 개발 대회를 찾고 브라우저에서 관심 일정과 캘린더 파일을 관리하는 오픈소스 디렉터리.
2. **해결하는 문제**
   대회 공지가 여러 플랫폼에 흩어져 있고 신청 마감과 대회 시작 시각의 의미가 달라 놓치기 쉽다는 점.
3. **기술적 차별점**
   공식 API와 수동 검증의 분리, 런타임 스키마 검증, 최신 시각 비교, 번들 fallback, 클라이언트 전용 개인정보 최소화.
4. **오픈소스 영향**
   데이터 출처와 정정 과정을 공개하고, 다른 기여자가 새 출처와 검증 규칙을 추가할 수 있음.
5. **지원 사용 계획**
   유지관리, 테스트, 접근성 검증, 데이터 출처 확대, 기여자 온보딩에 Codex를 어떻게 사용할지 구체적인 주간 작업으로 설명.
6. **증거 링크**
   공개 저장소, 라이선스, 기여 문서, 릴리스, 실제 배포, 핵심 이슈와 Pull Request.

## 신청 직전 최종 감사

- 신청 계정과 저장소 소유권이 일치하는가
- 저장소가 신청 기간 내내 공개 상태인가
- README의 라이브 링크와 화면이 실제로 동작하는가
- 라이선스와 제3자 고지가 누락되지 않았는가
- 최근 커밋이 단순 생성물이 아니라 유지관리 활동을 보여 주는가
- 지원을 사용할 구체적인 6개월 계획이 있는가
- 사용자가 없는 상태에서 수치나 커뮤니티 효과를 과장하지 않았는가
- 프로그램의 최신 공식 자격, 제외 대상, 개인정보 조건을 다시 확인했는가

## 현실적인 신청 시점

공개 저장소와 프로덕션 배포만으로 기술적 기반은 갖출 수 있지만, 바로 신청하는 것보다 다음 최소 증거가 생긴 뒤 신청하는 편이 설득력이 높습니다.

- 검증된 첫 공개 릴리스
- 실제 사용자의 피드백 또는 사용 사례
- 공개 이슈를 통한 한 차례 이상의 개선
- 외부 기여 또는 기여 가능한 이슈 목록
- 최소 몇 주간의 안정적인 데이터 갱신 기록

프로그램이 신규 프로젝트도 명시적으로 허용하거나 신청 마감이 먼저 온다면, 현재 상태를 솔직히 밝히고 6개월 유지관리 계획을 중심으로 신청합니다.
